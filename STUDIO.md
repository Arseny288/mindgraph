# STUDIO.md — переработка интерфейса в рабочую поверхность агента

Читай вместе с `mission.md`, `HANDOFF.md`, `NEXT_SESSION.md`. Этот файл описывает
одну задачу: превратить вьюер из картинки в единственное место, где пользователь
работает с агентом.

Все идентификаторы, комментарии, строки интерфейса и события — на английском.
Русский только в этом файле.

---

## 0. Где мы сейчас и что должно стать

**Сейчас.** `viewer/` — статика: читает `graph.json`, рисует React Flow + dagre,
композер в правом верхнем углу — неактивная заглушка. Агент на pi живёт отдельным
процессом, пишет события в JSONL, работает в worktree, соблюдает границы зон.
Эти две половины не соединены: пользователь либо смотрит на граф, либо запускает
агента в терминале.

**Должно стать.** Одна команда поднимает локальную студию. Пользователь ставит
задачу, кликнув на узел. Видит план **до** исполнения, подсвеченный прямо на графе.
Смотрит, как агент работает внутри зоны, и видит момент, когда агент упирается
в стену. Получает вердикт цветом на узле и диф. Принимает или сносит одной кнопкой.

**Не трогаем.** Схему `graph.json`. Манифест `.mindvibe/nodes.yaml` и правило,
что LLM не переименовывает существующие узлы. Механику границ записи и worktree.
Набор инструментов агента.

---

## 1. Чего не делать

- **Никакого файлового дерева.** Как только оно появится, пользователь переедет
  в него, а граф станет декорацией.
- **Никакого чата как главного интерфейса.** Лента событий — это лента событий,
  а не переписка. Главный объект на экране — граф, не диалог.
- Никаких аккаунтов, облака, БД. Всё локально, состояние в файлах.
- Не писать свой слой над LLM-провайдерами: их даёт `pi-ai`.
- Не хранить состояние сессии в браузере. Перезагрузка страницы посреди работы
  агента должна восстановить ровно ту же картинку из `GET /api/state`.
- Не расширять поддержку языков. Только Python.

## 2. Архитектура

Новая команда:

```
mindvibe studio [path]        # поднять студию на репозитории, открыть браузер
  --port 5173
  --no-open
  --fake-verdicts             # временно, см. §11
```

Один процесс, четыре роли:

1. отдаёт статику вьюера;
2. REST + SSE для канваса;
3. супервизор дочернего процесса TS-агента (spawn, stdin/stdout, kill);
4. файловый watcher репозитория.

**Источник правды — файлы, не память процесса:**

```
.mindvibe/
  graph.json
  nodes.yaml
  layout.json                 # позиции узлов, руками двинутые пользователем
  studio.lock                 # pid + port, защита от второго инстанса
  sessions/
    <session_id>/
      meta.json               # состояние, scope, prompt, plan, verdict
      events.jsonl            # то, что пишет агент (формат уже есть)
      worktree/               # ветка исполнения
```

Студия — это read-through над этими файлами. Если процесс убили и подняли заново,
он поднимает последнюю незавершённую сессию из `meta.json` и продолжает показывать
её состояние. Один инстанс на репозиторий: при живом `studio.lock` вторая команда
не поднимает сервер, а открывает браузер на существующий порт.

## 3. Машина состояний сессии

```
idle ──plan──▶ planning ──▶ plan_ready ──run──▶ executing ──▶ verifying ──▶ review
                   │             │                  │             │            │
                   └──error──────┴────abort─────────┴─────────────┘            │
                                                                        apply ─┤─ applied
                                                                      discard ─┴─ discarded
```

Правила:

- В каждом состоянии на экране ровно **одна** главная кнопка. `idle` → Plan.
  `plan_ready` → Run. `executing` → Stop. `review` → Apply (Discard рядом, вторичной).
- Из `plan_ready` можно уйти обратно в `idle` (Discard plan) без последствий:
  планирование ничего не записало.
- `abort` во время `executing` = kill процесса агента + worktree остаётся для
  осмотра, состояние → `review` с вердиктом `aborted`.
- `apply` возможен только из `review` и только если пользователь видел диф
  (сервер этого не проверяет, но кнопка не активна, пока диф не загружен).
- Пока сессия не в терминальном состоянии, новую начать нельзя. Композер
  заблокирован с честной подписью, что сейчас происходит.

## 4. HTTP API

Все ответы содержат `graph_version` (хэш `graph.json`). Если клиент видит чужой
`graph_version` — он перезагружает граф, а не рисует поверх старого.

```
GET  /api/graph                → graph.json + layout.json
GET  /api/state                → { session: {...} | null, graph_version, freshness }
POST /api/plan                 { scope_node_id | null, prompt } → { session_id }
POST /api/execute              { session_id }
POST /api/abort                { session_id }
GET  /api/diff?session_id=     → унифицированный диф, сгруппированный по узлам
POST /api/apply                { session_id }
POST /api/discard              { session_id }
POST /api/nodes                { title, symbol_ids[] }  → создать узел из Unassigned
POST /api/layout               { node_id, x, y }        → сохранить позицию
POST /api/rebuild              → полный пересчёт графа
GET  /api/events               → SSE, поток событий текущей сессии
```

SSE: при подключении сервер отдаёт **весь** `events.jsonl` текущей сессии,
потом стримит новое. Так перезагрузка страницы даёт полную ленту без спецкода.
Клиент переподключается с backoff, дублей избегаем по `seq` в событии.

## 5. Контракт событий

Агент уже пишет JSONL. Зафиксируй набор типов, которые канвас умеет рисовать,
и поле `v` (версия схемы) в каждом событии:

| type | обязательные поля | что делает UI |
|---|---|---|
| `session.started` | `scope_node_id` | фокусирует граф на зоне |
| `plan.ready` | `nodes[]`, `files[]`, `contracts[]`, `tests[]` | панель плана + подсветка |
| `node.entered` | `node_id` | узел переходит в active |
| `tool.called` | `tool`, `target` | строка в ленте, пульс на узле |
| `tool.denied` | `tool`, `target`, `owner_node_id`, `reason` | **см. §6.3** |
| `file.written` | `path`, `node_id` | счётчик правок на узле |
| `contract.blocked` | `contract_id`, `node_id` | отдельный вес в ленте |
| `tests.started` / `tests.finished` | `selected[]`, `ok/failed/unverified` | вердикт узла |
| `verdict` | `node_id`, `state`, `complete` | цвет узла |
| `error` | `message` | лента + состояние failed |
| `session.finished` | `outcome` | переход в review |

Неизвестный `type` рисуется как generic-строка. Канвас не падает от события,
которого не знает, — это единственный способ развивать агента и UI независимо.

## 6. Канвас

### 6.1 Что остаётся

Визуальный язык уже выбран, не переизобретай: фон `#FDFDFC` с тёплой точечной
сеткой, белые карточки без заливки, **цветная вертикальная полоса слева** (5
приглушённых цветов, детерминированно по имени узла), надпись-ярлык над карточкой,
бейдж-замок справа сверху, точка shared-символа справа снизу, smoothstep-рёбра
цветом узла-источника, скелетный граф (одно главное ребро на узел, остальные —
по наведению), никаких анимированных пульсаций на рёбрах.

Цветная полоса — это **идентичность** узла. Состояние узла нельзя кодировать
тем же каналом, иначе пользователь потеряет карту, которую выучил. Состояние
идёт обводкой, фоном карточки и бейджами.

### 6.2 Состояния узла

| состояние | как выглядит |
|---|---|
| `idle` | текущий вид |
| `in_plan` | сплошная обводка, карточка чуть приподнята |
| `out_of_scope` | во время исполнения — прозрачность 35%, рёбра бледнее |
| `active` | обводка цвета узла + бегущая линия по периметру карточки, не по ребру |
| `ok` | зелёный бейдж-галочка |
| `failed` | красный бейдж |
| `unverified` | серо-жёлтый бейдж, подпись «not covered by tests» |
| `incomplete impact` | маленький значок рядом с вердиктом, не меняет его цвет |

Про последнее: `complete=false` встречается часто (резолвер импортов отложен),
поэтому он **не понижает** вердикт, а показывается вторым признаком. Иначе всё
станет вечно жёлтым и цвет перестанут читать.

Во время исполнения глушение всего, что вне зоны, — это и есть визуальная
метафора стены. Не декоративная: пользователь буквально видит, что агент заперт.

### 6.3 Отказ инструмента — главный кадр продукта

`tool.denied` рисуется **на границе**, а не тостом в углу:

- короткая вспышка по контуру узла-владельца, куда агент пытался залезть,
  и линия от активного узла к нему, которая гаснет за ~600 мс;
- постоянная запись в ленте: какой инструмент, какой путь, чей это узел;
- счётчик отказов на панели сессии: `blocked: 3`.

Это доказательство, что стена настоящая. Прятать его — значит выбросить главную
ценность инструмента.

## 7. Композер и план

Композер перестаёт быть «отправить» и становится **Plan**.

- Чип области слева от поля: `Whole project` или имя узла. Клик по узлу на
  канвасе меняет чип. Esc сбрасывает в `Whole project`.
- Кнопка называется `Plan`, не `Send`. Планирование выполняется агентом
  с **read-only инструментами** — записать он физически не может.
- Результат — не текст, а панель: затронутые узлы (подсвечены на графе),
  файлы, контракты, которые придётся тронуть, тесты, которые будут прогнаны.
- **Предохранитель:** если план задевает больше трёх узлов, `Run` неактивен.
  Подпись прямая и с выходом: `This touches 5 areas. Pick one and describe a
  smaller change.` Плюс список этих узлов кликабельными чипами, чтобы сузить
  область одним нажатием.

Одна и та же формулировка действия проходит через весь поток: кнопка `Plan` →
состояние `Planning` → панель `Plan`. Кнопка `Apply` → тост `Applied`.

---

## 8. Лента событий

Правая панель, вертикальная, свёрнута по умолчанию до узкой полосы с последним
событием; раскрывается кликом.

- События группируются по узлу, внутри — по времени.
- Автоскролл только если пользователь стоит внизу. Проскроллил вверх — не дёргать.
- Отказы и `contract.blocked` рисуются заметнее остальных строк.
- Внизу ленты — то, чем сессия закончилась, а не пустота.

---

## 9. Ревью и приёмка

Состояние `review`:

- Сверху — вердикт: три состояния, плюс значок неполного impact, плюс строка
  «green means: nothing broke, as far as the tests know». Формулировка честная,
  не рекламная.
- Диф сгруппирован **по узлам**, не по путям файлов. Пользователь мыслит зонами.
- `Apply` — коммит worktree в рабочее дерево. `Discard` — снос worktree,
  граф возвращается в состояние до сессии.
- После `Apply` граф пересчитывается инкрементально, изменённые узлы коротко
  подсвечиваются — единственный момент немотивированной анимации, который
  оправдан: он показывает, что именно поменялось.

---

## 10. Свежесть графа, watcher, Unassigned

- В шапке всегда честная строка: `Graph built 3 min ago` + кнопка `Rebuild`.
  Если по логам её жмут часто — это баг инкрементального пути, а не любовь
  пользователей к кнопкам.
- Watcher: хэш AST на файл, пересчёт только изменённых, impact пересобирается
  локально. Порог — обновление меньше секунды после сохранения файла, иначе
  пользователь уходит смотреть в редактор.
- Символы, не приписанные ни к одному узлу (написанные руками или созданные
  агентом — путь **один и тот же**), падают в служебный узел `Unassigned`:
  визуально отличный, пунктирный, с инлайновым полем `name this area`.
  Имя, данное пользователем, фиксируется в `nodes.yaml` и становится истиной.
  Граф растёт по одному узлу за раз, а не переучреждается целиком.

## 11. Что можно замокать

Фаза 3 (реальный прогон тестов) может быть ещё не готова. Флаг
`--fake-verdicts` подставляет вердикты случайно, **но в настоящем формате**
и через настоящий путь событий. Интерфейс строится параллельно фазе 3, и когда
она приземляется — меняется только источник, не UI. Флаг убирается в тот же день.

## 12. Производительность и отказы

- `backdrop-filter` отключать при зуме < 0.6, иначе панорама дёргается.
- Позиции узлов — в `layout.json`. Автолейаут при каждом открытии = прыгающие
  узлы = потерянная карта.
- Анимировать только `opacity` и `transform`.
- Агент умер — сессия переходит в `failed`, worktree сохраняется, в ленте
  последняя реальная строка, а не «что-то пошло не так».
- Порт занят — брать следующий свободный и печатать его, не падать.
- Пустое состояние (`graph.json` ещё не построен) — не белый экран, а прогресс
  скана с числом обработанных файлов.

## 13. Приёмка

Сценарий записывается как чек-лист и прогоняется на **чужом** репозитории
(20–50k строк, не из `Testing_libs/`):

1. `mindvibe studio .` в незнакомом проекте — граф на экране, узлы читаемые.
2. Клик по узлу → чип области меняется.
3. Задача в композер → `Plan` → панель плана, затронутые узлы подсвечены,
   ничего в репозитории не изменилось (проверить `git status` — пусто).
4. Задача, задевающая пять узлов → `Run` заблокирован, подсказка внятная.
5. `Run` → узлы вне зоны приглушены, лента идёт, активный узел виден.
6. Задача, которая заведомо требует правки чужого узла → отказ виден
   на канвасе и в ленте.
7. Вердикт на узле, диф по узлам, `Discard` → `git status` снова пуст.
8. Повтор, `Apply` → изменение в рабочем дереве, граф обновился сам.

Главная метрика — прежняя: **чужой человек за 90 секунд от установки до
принятого зелёного изменения.** Замеряй секундомером на живом человеке,
а не на себе: ты знаешь, куда кликать.

## 14. Порядок работы

Останавливайся после каждого шага и показывай результат.

1. Процесс `studio`: статика + `/api/graph` + `/api/state` + SSE-заглушка.
   Канвас пока прежний, но живёт на сервере и переживает перезагрузку страницы.
2. Машина состояний + `plan` на read-only инструментах + панель плана
   + подсветка затронутых узлов + предохранитель на три узла.
3. `execute`: супервизор агента, лента событий, состояния узлов, приглушение
   вне зоны, отрисовка `tool.denied`.
4. Вердикты, диф по узлам, `Apply` / `Discard`.
5. Watcher, инкрементальный пересчёт, `Unassigned` с именованием.

Если в этом файле что-то противоречиво или невозможно — остановись и спроси,
не изобретай замену.
