## 1. Контекст: что строим и зачем

Продукт — инструмент вайб-кодинга поверх семантического графа кодовой базы. Пользователь видит проект не как дерево файлов, а как граф смысловых узлов (фича, домен, слой). Он выбирает узел и ставит задачу. Агент работает **только внутри узла**.

Ценность не в красивом графе и не в модели. Ценность в цикле принуждения:

1. **impact-граф** — статический анализ (`call` / `uses` / `inherits` + транзитивное замыкание). Каркас уже есть.
2. **модель владения** — у каждого блока есть узел-хозяин. Блоки, используемые несколькими узлами, — это «контракты»: их сигнатуру нельзя менять без явного согласования.
3. **запертый агент** — агент правит только файлы/символы своей зоны. Проверка механическая, а не «мы попросили модель не лезть».
4. **проверка = тесты** — прогон тестов затронутых зон плюс контрактные тесты. Зелёные → «не сломал, насколько тесты знают».

Ключевое архитектурное решение, которое ты реализуешь: **границу нельзя навешивать хуком поверх агента, у которого есть универсальный `write`.** Агент получает набор инструментов, у которых записи вне зоны просто нет как операции. Это не забор, это отсутствие двери.

Раскладка стека:

- **Python-часть (`mindgraph`)** — мозг. Извлекает граф, считает impact, владение, контракты, границы. Остаётся на Python. Порт на TypeScript **не делать**.
- **TypeScript-часть (`agent/`)** — руки. Собственный агент поверх библиотек `pi` (`pi-agent-core` + `pi-ai`), со своими инструментами.
- Связь между ними — **CLI с JSON на stdout**. TS-сторона ничего не знает про внутренности extractor'а, только про схему JSON.

## ФАЗА 0 — Гигиена (блокирующая)

Всё, что построим дальше, унаследует эти дефекты, поэтому чиним сразу. Задачи по убыванию важности.

### 0.1 `--serve` ломается при обычной установке

Сейчас `pyproject.toml` пакует только `mindgraph/`, а `viewer/` лежит рядом с пакетом и в wheel не попадает. Работает только потому, что стоит `pip install -e .` и файлы остаются на месте. После честного `pip install .` сервер будет искать `viewer/` в site-packages и отдавать 404.

**Сделать:** перенести `viewer/` внутрь пакета (или подключить как package-data), читать ресурсы через `importlib.resources`.

**Критерий приёмки:** в чистом venv `pip install .` (без `-e`), запуск сервера, `curl` возвращает `index.html` и все статические ассеты со статусом 200. Тест, который это проверяет, — в `tests/`.

### 0.2 Вьюер целиком на CDN

`main.jsx` тянет React / ReactFlow / dagre с `esm.sh`, стили с `unpkg.com`. Офлайн граф не отрисуется вообще. Для локального инструмента внешняя сетевая зависимость на рантайме недопустима.

**Сделать:** вендорить зависимости в пакет с фиксированными версиями. Если для этого нужен билд-шаг (esbuild/vite) — добавь его, но собранные артефакты должны попадать в wheel, чтобы у пользователя не было требования иметь node.

**Критерий приёмки:** отключаешь сеть — граф открывается и рисуется полностью.

### 0.3 Смена конфига не инвалидирует кэш

`repo_hash` учитывает только `.py`-файлы и игноры. Переключение `provider`, `model`, `entry_points` или диапазона узлов молча вернёт старый `graph.json` со старой группировкой и старыми owners.

**Сделать:** считать `config_fingerprint` — хэш эффективного конфига (провайдер, модель, версия промпта, entry_points, параметры группировки, версия extractor'а). Писать его в `graph.json`, сверять при загрузке кэша. Не совпал → пересчёт.

**Критерий приёмки:** тест меняет модель в конфиге, запускает повторно, получает пересчитанный граф, а не кэш.

### 0.4 Секрет

Реальный ключ DeepSeek лежит в `.env` на диске. В git не попал, `.gitignore` работает — это нормально, но ключ засветился в рабочей сессии.

**Сделать:** ключ читается только из окружения. Добавь явную проверку, что значения из `.env` никогда не попадают в `graph.json`, в логи и в артефакты сессий.

**Отдельно, руками (не задача агента):** ключ ротировать.

### 0.5 Батчинг >1500 символов

В `group.py` захардкожен один вызов, хотя спека §3 требует батчинг. На больших репах промпт раздувается и упирается в лимиты.

**Сделать:** батчинг по спеке. Детерминированное разбиение (одинаковый вход → одинаковые батчи), склейка результатов, обработка частичного отказа батча.

**Критерий приёмки:** прогон на репо, где вход заведомо больше лимита, — успешный результат и стабильный между запусками.

### 0.6 Прогресс

При долгом LLM-вызове CLI молчит десятки секунд, непонятно, жив ли процесс.

**Сделать:** лог этапов в **stderr** (stdout остаётся чистым для JSON — это важно для фазы 1). Флаг `--verbose`. Показывать текущий этап, номер батча из общего числа.

## ФАЗА 1 — `mindgraph` как стабильный JSON-контракт

Python-часть превращается в инструмент, который вызывают программно. Требования ко всем командам:

- машинный результат — **только в stdout**, только валидный JSON;
- все логи, прогресс, предупреждения — **в stderr**;
- каждый JSON-ответ содержит `"schema_version"`;
- осмысленные коды возврата: `0` — успех, `1` — ошибка выполнения, `2` — неверные аргументы, `3` — нарушение границы (см. `verify`);
- флаг `--json` там, где у команды есть человекочитаемый режим.

### Команды

| Команда | Назначение |
|---|---|
| `mindgraph scan <dir>` | Построить/обновить граф, записать `graph.json` |
| `mindgraph graph --json` | Весь граф: узлы, рёбра, метаданные |
| `mindgraph node <id> --json` | Один узел: файлы, символы, зона владения, контракты, тесты |
| `mindgraph impact <symbol\|file> [--depth N] --json` | Транзитивное множество затронутого |
| `mindgraph boundary <node_id> --json` | Границы зоны: allow-globs, deny-globs, контрактные символы |
| `mindgraph tests --for-node <id>` / `--for-diff <path>` | Какие тесты прогонять |
| `mindgraph verify --node <id> --diff <path\|-> ` | Проверить диф против границы узла |

### 1.1 Модель владения

Каждый символ/файл принадлежит ровно одному узлу-хозяину. Символ, используемый более чем одним узлом, помечается как **контракт**: у него фиксируется сигнатура и её хэш.

В `node --json` отдавать:
- `owned`: пути и символы, которые узел может править свободно;
- `contracts`: символы, которые узел использует, но не владеет, — читать можно, менять сигнатуру нельзя;
- `foreign`: всё остальное — недоступно даже на чтение по умолчанию.

### 1.2 `boundary`

Возвращает то, что TS-сторона превратит в проверку пути:

```json
{
  "schema_version": "1",
  "node_id": "auth",
  "allow_write": ["app/auth/**", "tests/auth/**"],
  "deny_write": ["**"],
  "allow_read": ["app/auth/**", "app/models.py"],
  "contracts": [
    {"symbol": "User.check_password", "signature_hash": "..."}
  ]
}
```

Порядок разрешения — deny по умолчанию, allow точечно. Пути нормализуй, `..` и симлинки за пределы репо отсекай.

### 1.3 `verify`

Принимает unified diff на stdin или файлом, отвечает вердиктом:

```json
{
  "schema_version": "1",
  "ok": false,
  "violations": [
    {"path": "app/billing/models.py", "reason": "outside_node_zone", "owner": "billing"},
    {"symbol": "User.check_password", "reason": "contract_signature_changed"}
  ]
}
```

Проверка **механическая**, по путям и по сигнатурам, без участия LLM. Изменение сигнатуры контракта — нарушение, даже если файл в зоне узла.

**Критерий приёмки фазы:** на microblog из `Testing_libs/` все семь команд отрабатывают, JSON валидируется схемой, `verify` ловит подсунутый диф, трогающий чужой файл, и возвращает код 3.

## ФАЗА 2 — Скелет агента на `pi`

Новый пакет `agent/` в корне репозитория. TypeScript.

### 2.1 Перед началом

`pi` публикуется под разными неймспейсами (`@earendil-works/*` и `@mariozechner/*`) и API меняется. **Проверь актуальные имена пакетов и README `pi-agent-core` / `pi-ai` перед установкой. Если реальный API расходится с тем, что описано ниже, — следуй README, а не этому документу**, и отметь расхождение в отчёте.

Берём из `pi` только нижние слои: агентный цикл (`pi-agent-core`) и унифицированный доступ к провайдерам (`pi-ai`). **TUI не подключаем** — поверхность продукта не терминал, а канвас-вьюер. Первый режим работы — headless.

### 2.2 Клиент к mindgraph

Тонкая обёртка, вызывающая Python-CLI подпроцессом, парсящая stdout как JSON, пробрасывающая stderr в лог. Проверяет `schema_version` и падает громко при несовпадении. Никакой другой связи между TS и Python нет.

### 2.3 Инструменты агента

Стандартные `read/write/edit/bash` **не регистрируем**. Вместо них:

- `list_nodes()` — узлы графа с краткими описаниями;
- `open_node(id)` — контекст узла: файлы зоны, контракты с сигнатурами, ближайшее кольцо impact. Это заменяет «прочитать весь репозиторий»;
- `read_file(path)` — отказ, если путь не в `allow_read`;
- `edit_file(path, ...)` — отказ, если путь не в `allow_write`. Проверка до записи, а не после;
- `create_file(path, ...)` — то же правило;
- `run_tests()` — без аргументов от модели. Команду формирует `mindgraph tests --for-node`, агент не выбирает, что запускать, и произвольную оболочку не получает;
- `request_contract_change(symbol, rationale)` — не меняет ничего. Останавливает сессию и выносит запрос человеку.

Универсального `bash` нет вообще. Если агенту нужна операция, которой нет в списке, — правильный ответ «инструмента нет», а не обходной путь.

### 2.4 Изоляция

Каждая сессия узла — в отдельном `git worktree`. Откат при нарушении или красных тестах бесплатный: снести worktree.

### 2.5 Защита в глубину

После каждого хода агента, независимо от того, что показали инструменты:

1. взять `git diff` в worktree;
2. прогнать через `mindgraph verify --node <id>`;
3. код 3 → откат хода, запись инцидента в лог сессии, попытка не засчитывается.

Инструмент, который пропустил запись вне зоны, — это баг с высоким приоритетом. Логируй такие случаи отдельно.

### 2.6 Точка входа

```
mindvibe agent --node <id> --task "..." [--json]
```

В `--json` — поток событий JSONL (начало хода, вызов инструмента, отказ инструмента, вердикт verify, результат тестов). Это будущий транспорт для вьюера, поэтому формат событий фиксируй сразу и версионируй.

**Критерий приёмки фазы:** на microblog агент выполняет осмысленную правку внутри одного узла; попытка (в тесте — принудительная) записать в чужой файл отбивается на уровне инструмента; подсунутый в обход инструментов диф ловится шагом verify; тесты узла прогоняются и вердикт попадает в поток событий.
