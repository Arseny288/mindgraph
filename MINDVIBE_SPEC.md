# mindvibe — спецификация для реализации

Построй CLI-инструмент `mindvibe`, который сканирует Python-репозиторий, разбивает его на **смысловые узлы** и показывает граф связей между ними в браузере.

Реализуй ровно то, что описано ниже. Если что-то в спеке противоречиво или невозможно — остановись и спроси, не изобретай замену.

---

## 0. Что это и чем не является

Смысловой узел — это единица замысла («Аутентификация», «Хранилище», «Уведомления»), а **не** файл, не модуль и не класс. Один узел обычно размазан по нескольким файлам; один файл может принадлежать нескольким узлам. Это оверлей поверх кода, а не разбиение кода.

**Не делай:**
- узел = файл или узел = директория (это уже есть в любом файловом дереве, ценности ноль)
- редактирование кода, применение патчей, запись в репозиторий пользователя — на этом этапе инструмент строго read-only
- бэкенд-сервер с БД, аккаунтами, вотчерами файловой системы
- поддержку языков кроме Python

## 1. CLI

```
mindvibe <path>            # анализ + запись .mindvibe/graph.json
mindvibe <path> --serve    # то же + поднять вьюер на localhost:5173 и открыть браузер
mindvibe <path> --no-llm   # только статический анализ, без группировки в узлы
mindvibe <path> --stats    # напечатать метрики (см. §6) и выйти
```

- `<path>` — корень репозитория. По умолчанию `.`
- Результат кладётся в `<path>/.mindvibe/graph.json`
- Если `.mindvibe/graph.json` уже есть и `graph.json.repo_hash` совпадает — переиспользуй, не пересчитывай, если не передан `--force`
- Игнорируй: `.git`, `venv`, `.venv`, `node_modules`, `__pycache__`, `.mindvibe`, `build`, `dist`, `*.egg-info`, содержимое `.gitignore`
- Никогда не падай целиком из-за одного файла: файл с синтаксической ошибкой → предупреждение в stderr, файл пропускается, остальное продолжает работать

## 2. Этап A — статическое извлечение символов

Чистый `ast` из стандартной библиотеки. Никаких внешних анализаторов на этом этапе, никаких запусков пользовательского кода (`import` анализируемого проекта запрещён — только парсинг исходников).

Для каждого `FunctionDef`, `AsyncFunctionDef`, `ClassDef` собери:

| поле | как получить |
|---|---|
| `id` | путь модуля от корня репы + вложенность, точками: `auth.login.verify_token`, `db.models.User.save` |
| `kind` | `function` \| `method` \| `class` |
| `file` | путь относительно корня репы |
| `lines` | `[node.lineno, node.end_lineno]` |
| `sig` | текст сигнатуры, восстановленный из `ast.arguments` + аннотаций (`ast.unparse` по подузлам) |
| `doc` | `ast.get_docstring(node)`, первые 200 символов, `null` если нет |
| `loc` | `end_lineno - lineno + 1` |

Вложенные функции внутри функций **не** извлекай как отдельные символы — они часть родителя.

### Рёбра

Строй два типа рёбер, `imports` и `calls`.

**Импорты.** Для каждого файла построй таблицу `local_name -> fully_qualified_id` из `Import` и `ImportFrom`. Резолви только внутрирепозиторные модули; всё, что не резолвится в файл внутри репы, считается внешним и в граф не попадает (но сохрани список внешних пакетов в `graph.external` — пригодится для группировки).

Относительные импорты (`from ..models import User`) резолви через позицию файла в дереве.

**Вызовы.** Обходя тело каждого символа, лови `ast.Call`:
- `func` типа `Name` → ищи в таблице импортов файла, потом среди символов того же модуля
- `func` типа `Attribute` с базой `Name` → если база в таблице импортов, резолвь как `module.attr`
- `self.foo()` → резолвь в метод того же класса (или его баз, если базы найдены в репе)
- всё остальное не резолвится — молча пропускай

Это даст примерно 80% реальных вызовов, и этого достаточно. Не пытайся делать вывод типов.

Ребро — `{"from": "<symbol_id>", "to": "<symbol_id>", "type": "call"|"import"}`. Дедуплицируй, храни `weight` = число вхождений. Само-рёбра выкинь.

## 3. Этап B — группировка в смысловые узлы

Через Anthropic API (`ANTHROPIC_API_KEY` из окружения; при отсутствии — сообщи и работай как `--no-llm`).

**Критично: в промпт уходят только `id`, `sig`, `doc` и рёбра. Тела функций не отправляются никогда.** Именно это делает возможным анализ большой репы в один заход и является сутью подхода.

Формат запроса к модели:
- system: объясняет, что нужно сгруппировать символы в 5–15 смысловых узлов по назначению, а не по расположению в файлах; имена узлов — короткие, на русском, в терминах предметной области, не в терминах реализации («Аутентификация», не «Модуль auth»)
- user: JSON со списком символов (`id`, `sig`, `doc`) и списком рёбер
- Требуй ответ строго в JSON, без markdown-заграждений и преамбулы:

```json
{"nodes": [{"name": "Аутентификация",
            "summary": "одно предложение о назначении узла",
            "symbols": ["auth.login.verify_token", "auth.tokens.issue"]}]}
```

Обработка ответа:
- парси устойчиво: сначала попытка `json.loads`, при неудаче — срезать ```json-заграждения и повторить
- **валидируй**: каждый `id` из ответа обязан существовать в `graph.symbols`; несуществующие — отбросить и записать в `graph.warnings`
- каждый символ обязан попасть ровно в один узел; **все неназначенные символы собери в служебный узел `Прочее`** и укажи их число в статистике — это твой честный индикатор качества группировки, не прячь его
- если символов больше 1500, режь на батчи по модулям, группируй по батчам, потом вторым запросом слей близкие узлы по именам и summary

### Рёбра между узлами

Ребро узел→узел выводится, а не спрашивается у модели: для каждого символьного ребра `A.sym -> B.sym`, где `node(A.sym) != node(B.sym)`, инкрементируй `weight` соответствующего узлового ребра. Ребра с `weight == 1` пометь `weak: true` (вьюер рисует их бледнее).

## 4. Этап C — вычисление shared-слоя

Это самая важная часть инструмента, не пропусти её и не сведи к строчке в логе.

Для каждого символа посчитай `owners` — множество узлов, из которых он **достижим** по рёбрам `calls`/`imports` (обход графа символов в обратном направлении, глубина не ограничена, циклы обрабатывай через visited-множество).

- `len(owners) <= 1` → символ приватен для узла
- `len(owners) > 1` → символ **shared**, в JSON поле `"shared": true`, плюс список `owners`

Это прямой ответ на вопрос, реализуемы ли вообще границы записи на данной кодовой базе: если shared-символов много, узлы нельзя изолировать. Метрику вывести обязательно (§6).

## 5. Формат `graph.json`

Единственный контракт между анализатором и вьюером. Вьюер не должен знать про Python и не должен ничего вычислять сам.

```json
{
  "version": 1,
  "repo": {"root": "/abs/path", "name": "myproject", "repo_hash": "sha256:...",
           "files": 42, "loc": 8130, "generated_at": "2026-08-21T12:00:00Z"},
  "symbols": [
    {"id": "auth.login.verify_token", "kind": "function", "file": "auth/login.py",
     "lines": [12, 34], "sig": "verify_token(t: str) -> User | None",
     "doc": "Проверяет JWT.", "loc": 23,
     "node": "Аутентификация", "shared": false, "owners": ["Аутентификация"]}
  ],
  "symbol_edges": [{"from": "auth.login.verify_token", "to": "db.users.get_by_id",
                    "type": "call", "weight": 2}],
  "nodes": [
    {"id": "n_auth", "name": "Аутентификация", "summary": "...",
     "symbols": ["auth.login.verify_token"], "files": ["auth/login.py"],
     "loc": 412, "shared_count": 3}
  ],
  "node_edges": [{"from": "n_auth", "to": "n_storage", "weight": 7, "weak": false}],
  "stats": {"symbols": 310, "unassigned": 12, "shared_symbols": 41,
            "shared_ratio": 0.13, "external": ["fastapi", "pydantic"]},
  "warnings": ["auth/legacy.py:88 syntax error, file skipped"]
}
```

Схему держи стабильной: любые будущие поля — только добавлением, без переименований.

## 6. Вывод `--stats`

Печатай в stdout человекочитаемо:

```
файлов 42 · символов 310 · строк 8130
узлов 7 · не назначено 12 (3.9%)
shared-символов 41 (13.2%)   <- ключевая метрика
топ shared: db.session.get_db (5 узлов), utils.crypto.hash (4), config.settings (4)
```

Порог для интерпретации, выведи его подсказкой под цифрой: `shared_ratio` до ~15% — узлы изолируемы, границы записи осмысленны; выше ~30% — узлы протекают друг в друга, определение узла нужно менять.

## 7. Вьюер

Отдельная статика в `viewer/`, поднимается `--serve` через `http.server` (или vite dev-сервер, если ставишь npm-зависимости). Читает `graph.json`, рендерит React Flow + dagre (layered layout, направление сверху вниз).

Визуальный язык:

- фон — светлая точечная сетка (dot grid), как миллиметровка
- узел — карточка со стеклянным эффектом: полупрозрачный белый фон, лёгкая тень, скруглённый угол, **цветная вертикальная полоса слева**, цвет из палитры приглушённых архивных тонов (5 цветов, детерминированно по имени узла)
- надпись `ФИЧА` мелким разреженным капсом над карточкой, цветом узла
- рёбра — smoothstep, окрашены в цвет узла-источника, `weak` — тоньше и бледнее
- **никаких анимированных пульсаций на рёбрах**
- при наведении на узел — подсветка всей цепочки его связей, остальное приглушается
- при загрузке — каскадное появление карточек по слоям, задержка ~40 мс на слой
- бейдж-замок в правом верхнем углу карточки — placeholder под будущие границы записи, пока просто индикатор
- клик по узлу — панель справа: summary, список файлов, список символов с сигнатурами, shared-символы отдельным блоком с пометкой, в какие ещё узлы они входят

Панель композера в правом верхнем углу («Весь проект» / поле ввода / счётчик узлов) свёрстай как неактивную заглушку — она под следующий этап, сейчас ничего не отправляет.

## 8. Структура проекта

```
mindvibe/
  cli.py            # argparse, оркестрация этапов
  extract.py        # этап A: ast → символы и рёбра
  group.py          # этап B: вызов API, валидация, узлы
  shared.py         # этап C: достижимость, shared-слой
  emit.py           # сборка и запись graph.json
  serve.py          # статик-сервер
viewer/
  index.html, main.jsx, nodes.jsx, theme.js
tests/
  fixtures/sample_repo/   # маленькая синтетическая репа, 8-10 файлов
  test_extract.py
  test_shared.py
```

`pyproject.toml` с entry point `mindvibe = mindvibe.cli:main`. Зависимости минимальны: `anthropic`, всё остальное — стандартная библиотека.

## 9. Тесты и приёмка

Собери в `tests/fixtures/sample_repo/` синтетическую репу с заранее известной структурой: два независимых кластера и один намеренно общий модуль-утилита, который используют оба.

Готово, когда:

1. `mindvibe tests/fixtures/sample_repo --no-llm` даёт ожидаемое число символов и рёбер (assert по точным числам)
2. Общий модуль из фикстуры детектируется как shared с обоими узлами в `owners`
3. Циклический импорт в фикстуре не вешает обход достижимости
4. Файл с синтаксической ошибкой попадает в `warnings`, остальные файлы обрабатываются
5. `mindvibe . --serve` на самом себе открывает граф, узлы соответствуют реальным модулям, панель узла показывает файлы и символы
6. Повторный запуск без `--force` не тратит вызовы API

## 10. Порядок работы

Делай по этапам, останавливайся после каждого и показывай результат:

1. `extract.py` + тесты на фикстуре → покажи сырой JSON символов и рёбер
2. `shared.py` + `--stats` без LLM → покажи цифры на моей настоящей репе
3. `group.py` → покажи получившиеся узлы текстом, до всякой визуализации
4. `viewer/` → только теперь картинка

Не начинай следующий этап, не показав предыдущий.
